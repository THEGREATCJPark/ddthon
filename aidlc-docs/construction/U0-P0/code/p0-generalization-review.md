# P0 과적합·환경 설정 점검

검토 기준: 현재 main a22e176 위 미커밋 P0 보완본, 승인된 p0-nl-acceptance-plan 개정 2. 사용자 요청에 따른 코드/설정 점검이며 이번 점검으로 제품 코드나 승인 범위를 변경하지 않는다.

## 판정

합성 P0의 실제 설치·검증·재사용 실적은 유효하다. 일반 패키지/새로운 저장 Skill/독립 설치 환경에 대한 일반화는 입증되지 않았으며 제품 실행부에 데모 결합이 남아 있다. 승인된 단일 합성 대상 한정 구현 자체가 절차 위반은 아니지만, 이를 일반 복구 제품 완성으로 표현하면 범위를 과장한다.

## 확인한 결합

1. cli._parse_work_requirements는 skillloop-demo-pkg==1.0.0 단 한 줄만 수용한다. 다른 버전·다른 패키지는 물론 같은 배포 이름의 구분자/대소문자 변형도 거절한다. 실제 read-only 함수 호출로 확인했다. 관찰 정규화가 범용이어도 실행 진입점은 범용이 아니다.
2. 자동 실행 허용을 코드의 _DEMO_SKILL_CONTENT exact digest와 비교한다. 승인되지 않은 Skill 자동 실행을 막는 목적은 타당하나 승인 정보가 코드 내 특정 예제와 결합돼 있다. 절차가 같은 다른 id의 digest는 불일치한다. 일반화를 위해 이 검사를 삭제하는 것은 부적절하며, 기존 승인/실행 확인 계약과 연결해야 한다.
3. reuse_service의 요구 버전·import 모듈은 envharness_p0.TARGET_VERSION/TARGET_IMPORT이고 index resolver도 failing/allow 두 이름만 처리한다. 새 Skill 등록만으로 다른 패키지를 적용할 수 없다.
4. 제품 runtime에서 tests/fixtures/indexes를 해석한다. pyproject의 패키지 목록은 skillloop이며 fixture 포함 선언은 없다. 현재 checkout/editable 실행과 일반 설치 배포는 구분해야 한다. 이번에 wheel-only 독립 설치 실험까지 수행한 것은 아니다.
5. 작업 연결 JSON 및 상태줄이 Codex session-context runtime의 개인 절대경로를 사용한다. 현 PC에서는 정상이나 해당 디렉터리 이동·삭제·다른 PC에서 그대로 사용할 수 없다. 작업별 경로 설정은 필요하지만 제품 설치 경로는 안정된 설치/등록 과정에서 만들어야 한다.
6. C9는 requirements 요청을 보고 지원 경로를 호출하고, 실패 관찰·검색·적용은 CLI가 실행한다. 자연어 업무 진입은 증명했으나 Agent가 독립적으로 환경 제약을 발견하고 범용 문제 해결 전략을 탐색했다는 증거는 아니다. P0 기존 절차 재사용과 P1 탐색을 구분해야 한다.

## 적절한 합성 테스트 설정

- 새 작업 venv, 로컬 빈 공급원, 성공 패키지 공급원, 기존 해결 Skill 준비는 오프라인 합성 환경 재현에 적절하다. 성공 결과 자체는 미리 넣지 않고 실제 pip·import를 실행한다.
- 실패 공급원은 운영자 준비 단계에서 설정된다. 실행 중 실패를 강제로 만들거나 요청 venv를 교체하지 않는다.
- requirements/store/usage/작업 Python 연결은 해결 정답이 아니다. 실제 경로 혼선을 막는 역할이 있다.
- 프로젝트 단위 C9 설치·상태줄 설정은 정상적인 통합 설정이다. 최신 테스트의 settings.local.json에 Python 명령 허용 항목도 존재하나 이것은 실행 권한이며 Skill 매칭 결과나 카운트를 대신하지 않는다. 이 항목의 생성 주체는 이번 점검에서 단정하지 않는다.
- 테스트의 무관한 두 번째 descriptor는 매칭 배제용이며 유효한 파일접근 해결 절차 구현을 증명하지 않는다.

## 사용자 실행 증거

사용자가 제공한 skillloop-p0-test-203704 로그의 run_id 09106bdcbd744149af3bc013690ab447에 대응하는 로컬 event가 존재한다. actual count=1, 실제 검증 evidence를 확인했다. 별도 read-only Python 프로세스로 같은 작업 venv의 version=1.0.0, IMPORT_OK를 다시 확인했다. 설치 재실행·추가 카운트·환경 초기화는 하지 않았다.

Agent 설명의 '허용된 index에서 찾지 못함'은 부정확하다. 최초 실패는 작업 환경의 기존 공급 경로(failing)이고 이후 Skill이 지정한 allow 경로로 실제 설치가 성공했다. 또한 실제 사내 proxy/DRM를 재현한 것은 아니며 패키지 공급 실패의 합성 대역이다.

## 다음 수정 후보와 AI-DLC 경계

우선순위는 (1) 제품 실행에서 세션 경로/테스트 fixture 의존 분리, (2) 기존 pip 액션의 대상·요구 버전·import 검증값을 명시적 입력/계약으로 전달, (3) exact 예제 whitelist를 승인된 실행 확인 방식과 연결, (4) 원 예제를 유지한 채 다른 합성 패키지/버전/Skill identity에서도 실제 실행되는 변형 검증이다. 여러 패키지·모든 pip 문법·실제 회사 인증까지 확장할 필요는 없다.

이 항목은 이전 승인 단일 대상 범위와 계약을 바꾸므로 자동 구현하지 않는다. 필요한 Functional Design/NFR/Code Plan 영향만 정리하고 승인을 거쳐 진행한다. 이전 P0 PASS는 제한된 범위의 증거로 보존한다.
